# 钉钉大V发言聚合看板（dingall-panel）

> **给接手的人 / AI 助手：请先完整读完这份文件再动任何代码。**
> 这个项目踩过的坑大多不是"写错了"，而是"不知道上游格式长这样"。
> 跳过这份文档直接改，有 90% 概率把某些源的解析搞坏，而且坏得很难发现
> （表现为"某个大V没同步""有漏"，而不是报错）。

## 1. 这是什么

把 7 个财经大V 的钉钉发言流（上游只提供 HTML，无 JSON、无 CORS）聚合到一个网页看板，
**实时推送**更新，供用户盘前/盘中快速扫一遍各家观点。

- **线上地址**：https://dingall-panel.onrender.com
- **代码仓库**：https://github.com/Haven-Lai/dingall-panel（本仓库，公开）
- **托管**：Render 免费实例（美国机房）。闲时休眠，首个请求要等冷启动 30~60 秒，属正常现象。
- **上游数据源**：`http://121.41.9.82:4380/dingall?a=<URL编码的群名>&o=1&r=1`
  这是一台小服务器，**别做密集压测**，1.5 秒一轮已经很接近它的舒适上限。

> 另一个模块：`/sentiment` 是「情绪看板」（大盘涨跌停 / 连板 / 板块热度）。
> 它大部分是**纯前端直连**东财 / 腾讯的，但涨跌停走势图（`/api/zt-kline`）和
> 涨停个股明细（`/api/zt-stocks`）走后端，详见 §4.5 / §4.6。`/api/health` 里 `ok:false` + `error:"全市场行情抓取失败"` 是
> `sentiment_core.py` 那条老刷新线报的，**不影响发言面板**，别去追这个 bug。

### 选手筛选：当前显示 / 默认显示是两套状态（2026-11-19 定稿）

选手到了 7 位，全铺开没法看。色标 chip 是**两段式**，一个管此刻、一个管下次：

| 点哪里 | 作用 | 存不存 |
|---|---|---|
| 框框**里面**的选手名字 | 切换这一位**此刻显示/不显示**，可多选，盘中随便切 | **不存**，刷新回到默认 |
| 色标行末尾「**全选 / 全不选**」 | 一把梭切换此刻显示哪几位（临时层） | **不存** |
| 框框**外面**的勾选框 + 「确定」 | 决定**每次打开网页默认看哪几位** | 存 localStorage |

⚠️ 「全选 / 全不选」只改 `visible`，**绝不碰 `pending`**。所以在全选状态下点「确定」，
默认仍然只认勾选框那几位（实测过，别把两者串起来）。

状态对应关系（`renderChips` 里一眼能看出来）：

- 蓝勾 + 蓝框 + 名字清晰 = 默认勾着、此刻在显示
- 蓝勾 + 名字变灰 = 默认勾着、但此刻被你关掉了
- 空框 + 灰 = 没进默认、此刻也不显示

⚠️ **这两层绝不能合并**（2026-11-19 前后改了四版才定，别再动）：
用户盘中要频繁点选手名字开关，那是「临时」。如果把点名字做成"只看这一个"，
或者把点名字顺手写进默认，都会让他每切一次就改一次设置。`visible`（此刻）
与 `pending`（默认）必须是两个独立集合，`saveVisible()` 只写 `pending`。

- `renderPosts` 先按 `isVisible` 筛，再叠加 `focus`（`focus` 只来自点帖内标签/人名）
- 把正在 `focus` 的那位关掉会自动退出 focus，免得停在空白页
- 一个都没勾就点确定 → 兜底成全选；点确定后当前显示也同步成默认那套
- ⚠️ 弹窗选择面板已被否掉（"搞得太复杂了，我还得点开一个对话框去选"）；
  别加回弹窗，别加「全选/清空」按钮
- 存 `{visible:[...], seen:[...]}`，`seen` 用来识别后来新增的选手：
  **新源自动进默认也自动显示**——绝不能因为一次旧选择把新源漏掉。
  ⚠️ `syncNewSources` 必须加 `hasSaved` 守卫，否则首次会把全部源当新源全勾上

- ⚠️ 后端 `/api/feed` 仍返回全部源的全部帖子，筛选只在渲染层做。

## 4. 架构：为什么这样写（别退回老路）

### 抓取（2026-11-05 重构，这是核心）

```
每个源一条独立线程  →  每 1.5 秒发一次 If-None-Match 条件请求
   ├─ 304（内容没变）：0 字节，直接跳过，不解析、不重建快照
   └─ 200（有变化）：解析 → _publish() → 版本号+1 → 叫醒所有 SSE 订阅者
```

- 环境变量 `DINGALL_POLL_SEC` 可调轮询间隔（默认 1.5，1.0 未压测过，别乱降）。
- **源之间互不拖累**：哪个源先变就立刻可见，不用等最慢的那个（龙头舵主偶尔要 6 秒）。
- ⚠️ **绝对不要改回「每 N 秒把全部源全量重抓一遍」**。老实现每轮搬 1.2MB，
  线上 `/api/feed` 实测 8~52 秒。改回去等于把用户最在意的"慢"重新装回来。

### 推送

- `/api/stream`（SSE）推送 `{ver, total, updated, added[], full, sources[]}`，约 500~700 字节。
- `_publish()` 顺手算出"相对上一版新增了哪些帖子"塞进 `added`，前端 `applyDelta()`
  就地插入 + 重排 + 高亮，**零往返**，不用再跨境拉 19KB 全量。
- 新增 > 12 条、或前端没有可信基线时推 `full:true`，前端老实拉全量。
- 前端连上 SSE 就停掉 5 秒轮询；断线自动退回轮询兜底。20 秒心跳，10 分钟主动断开重连。

### 快照与冷启动

- 内存快照 + 落盘 `data/feed_snapshot.json.gz`（**脏标记 + 独立线程每 20 秒写**）。
- ⚠️ 不要在 `_publish()` 里按时间节流直接写盘：会正好写在"只有第一个源抓完"的时刻，
  落盘结果是残缺的（实测只存下 309 条，实际 465 条）。
- 冷启动：有磁盘快照 → 首屏 0ms 顶旧数据；没有 → `build_feed()` **只等不抢**，
  等各源线程首次抓完（约 1.5 秒）。⚠️ 别再让它自己再并发抓一轮，12 个请求会压垮上游，首屏反而变 10 秒。

### 每日定时源

`DAILY_SOURCES = {"金甲": {"window": ("09:00", "09:40")}}` —— 金甲每天 09:27 左右只发一张图：

- 窗口内：1.5 秒高频轮询，确保当天那张图刚发出就抓到
- 窗口外且**当天已成功拉到过**：降频到 30 秒，少打扰上游
- 窗口外但当天还没拉到（服务刚重启）：仍会拉一次，否则整天看不到图
- 灯神 / 龙头舵主 / 金牌竞价这类白天持续发言的源**不要**加进来

### 发言人白名单（屏蔽群里的其他人）

`SPEAKER_WHITELIST = {"金牌竞价": {"嘉兴可爱范"}}` —— 「金牌竞价」实质是个群，几十人聊天，
群里只有群主有价值。白名单里的源**只保留指定发言人**，其余帖子在 `parse_posts()` 之后立刻丢弃：
不占快照、不进 SSE 增量、来源计数和前端 chip 一并变干净。网页和小程序同时生效
（两边读同一份 `/api/feed`，所以不需要改 `dingall-mini`）。

**为什么不用用户 ID 锚定**：上游 dingall 接口只吐纯文本昵称，整个响应里没有
`userId` / `staffId` / 头像 / 用户主页链接（602 个 `<a>` 全是同一个「只看Ta」，
指向的是整个来源而非某个人）。**这个接口上不存在可锚定的 ID**，所以只能靠结构信号锚定。

**改名自动锚定**（`_wl_learn`，别再手改名字）：

- 上游一次吐 **42 小时左右**的发言，所以「旧昵称彻底消失」要等一天多——不能拿它当判据
- 真正的判据是：**白名单里的人沉默超过 30 分钟（群里还在聊）+ 冒出一个从没见过的昵称 +
  它第一次开口正好在他销声之后**。改名在时间轴上就是这个形状
- 命中后先挂「待确认」90 秒（`WL_CONFIRM_SEC`），仍成立才写入别名表
  `data/speaker_whitelist.json`，新旧昵称**都保留**（改回来也认，历史发言不断档）
- 有人正常入群时，群主照样在说话，走不到这段分支，不会误伤
- 候选必须占近期发言 ≥25%（`WL_MIN_SHARE`），否则新群友刷几句就会把群主顶掉
- 实在认不出来（他真的整天没说话）：**临时显示全部并标 `unresolved`**，
  网页状态条会提示「昵称待识别」，绝不把该源清空成 0 条
- 排查入口：`/api/health` → `feed.whitelist`，能看到 `configured / aliases / active / mode / pending`
- 回归测试：`python tests/test_whitelist_anchor.py`（合成数据、不联网，验改名/入群/沉默/重启四种情形）

- 想恢复看全部：把这个源从字典里删掉即可
- 磁盘快照读取时也会再筛一遍（`_load_snapshot_from_disk`），
  否则旧快照会让别人发的垃圾先冒出来几秒

## 4.5 情绪看板：涨停 / 跌停家数走势图（2026-11-17 加）

页面：`/sentiment`（面板里的「情绪看板」tab）。这个页面是**纯前端直连**东财 / 腾讯，
不依赖后端，所以上面说的「发言面板」那套轮询 / SSE 跟它没关系。

**唯一走后端的就是这张涨跌停走势图**：

| 接口 | 作用 |
|---|---|
| `GET /api/zt-kline?limit=30` | 近 30 个交易日的涨停 / 首板 / 跌停家数，服务端抓东财 + 同花顺并缓存 |

为什么不让浏览器自己抓：凑 30 天要发 90 个跨域 JSONP，既占满浏览器对东财的并发
（本页板块榜还要用），又容易撞限流。服务端抓一次、全页共用。

**实现要点（改之前务必看）**

- 数据源用**东方财富涨停池 / 跌停池的 `tc` 字段**，跟页面卡片上那些数字**同一个接口**。
  ⚠️ 但东财的历史深度只有 ~15 个交易日，30 天视图必须靠**同花顺涨停池
  （`limit_up_pool` 带 `date` 参数，实测能回溯 35+ 个交易日）回补更早的日子**。
  东财优先是刻意的：最近 15 天要和卡片严丝合缝。混合后的接缝处两边差 0~2 家
  （11-04 东财 118 / 同花顺 116），图上肉眼看不出台阶。
- ⚠️ 两个池的排序字段**不通用**：涨停池用 `sort=fbt:asc`（首次封板时间），
  跌停池必须用 `sort=fund:asc`。给跌停池传 `fbt:asc` 会返回 `rc=0`、`tc` 正常但
  `pool` 为空 —— 看着像「没数据」，实际是排序字段不被接受。
- ⚠️ **跌停家数没有第二个源**：同花顺的 `dataapi/limit_down/*` 全是 404（没有跌停池接口），
  东财跌停池的深度跟涨停池一样只有 ~15 个交易日。所以**跌停线只画最近 15 天**，
  更早的日期 `dt` 给 `null` 让线断开。别拿别的口径凑数、更别补 0。
  服务端每天把结果**合并**进 `data/zt_history.json`（字段级「有值优先」，新扫的 `dt=null`
  不覆盖旧的数字），跌停的历史会随运行天数自己往前长，攒满 30 天就齐了。
- ⚠️ **同花顺首板口径要换算**，不能直接数 `high_days == "首板"`：
  `"2天2板" / "5天5板"` 是连续板（连板数 = N），`"5天3板" / "7天5板"` 是断板后重来
  （连板数 = 1）。只数字面会**少 3~15 家**（涨停多的大日子漏得最多）。
  按「`首板` + `N天M板`(N≠M)」数出来才对齐东财的 `lbc == 1`：多数日子完全相等，
  个别日子差 ≤4 只。
- **图上三条折线，同一坐标系**：涨停（红）、首板（橙）、跌停（绿），
  取**每个交易日收盘时的家数**。
  - 首板数从涨停池同一个响应的 `pool[].lbc`（连板数）数出来，取 `lbc == 1` 的家数，
    **不额外发请求**。算不出来（`pool` 被截断 / 拿不到明细）时给 `null` 让线断开，
    绝不能兜成 0 —— 0 会画成「那天一只首板都没有」，跟事实正好相反。
  - 为什么要这条线：首板是涨停的子集，看的是**两条线的间距**。涨停多而首板跟不上
    ＝资金全在抱团高位连板、新资金不敢接；涨停少但几乎全是首板＝冰点里已有资金试盘。
    只看涨停总数看不区分这两件事。
  - 不要改回蜡烛图。家数是日频单值，没有真实开高低收，硬用「前收 → 收盘」凑 K 线，
    相邻两根实体共用同一个端点会**完全重叠** —— 实测 11-02 收 125 家、11-03 收 48 家，
    画出来两根一样高，读到的是假信息。
  - 也不要拆成上下两个子图 / 双 y 轴。「红线掉下来和绿线靠近」本身就是退潮信号，
    两条线不在一个坐标里就看不出来。
  - `smooth` 保持 `false`。开平滑会让曲线在两点之间鼓出去、峰值虚高谷值虚低，读收盘家数会失真。
- 纵轴 `min: 0` 是硬要求，不从零基线起算会把 72 家和 125 家的差距放大成两倍。
- ⚠️ **字段口径**：每行是 `{d, zt, dt, first, live, final}`，`zt`/`dt`/`first` 才是家数
  （`first` 可能是 `null`，表示那天的首板数算不出来，不是 0）。
  早期版本叫 `zc`/`dc`，前端已做兜底。**改后端字段名时务必同步前端** ——
  取不到的字段会让 data 全是 `undefined`，ECharts 连 y 轴范围都算不出来，
  整个绘图区空白且**不报任何错**（这个坑踩过一次，排查了很久）。
- ⚠️ **别把 `symbol: "emptyCircle"` 写进 series 的 data 项**。那是 legend 的图标名，
  不是 series 的合法 symbol 类型，塞进去同样会让整条线静默消失。
  要空心点就写白填充 + 彩色描边：`{value, symbolSize: 9, itemStyle: {color:"#fff", borderColor, borderWidth: 2}}`。
- `final: false` 表示「今日还没收盘」（15:00 前），那个数字仍在变，前端画成空心点。
- 图表 DOM 刻意放在 `#content` **之外**（`#klsection`）：`render()` 每次都用
  `innerHTML` 重写 `#content`，图表放里面的话每 40 秒刷新就被销毁重建、闪一下。
- 前端渲染走 `static/echarts.min.js`（ECharts 5.4.4，1MB，**异步加载**，不挡首屏），
  由 `app.py` 的 `/echarts.min.js` 路由提供，已 gzip。
- 缓存：服务端内存 + `data/zt_history.json`（已 gitignore），历史日 **3 小时**一刷
  （全量重扫要打 ~90 个上游请求，别调太勤；历史日是定值，只有跨天才必须重扫）、
  当日那根 20 秒一刷；前端 `localStorage` 5 分钟内复用，避免每次刷新都请求。
  加字段时要同步处理**旧缓存**：磁盘缓存靠 `all("first" in r)` 和 `len(days) < 30`
  判断后强制重扫，前端靠缓存键版本号（`kl_zt_v1` → `kl_zt_v2`）丢掉旧 payload。
  漏了这几处的话，新线要等到跨天/清缓存才出现，很容易被误判成「东财没数据」。
- 排查：`curl -s https://dingall-panel.onrender.com/api/zt-kline | head -c 400`，
  正常返回 `{"ready": true, "days": 30, "dt_from": "2026-11-03", "series": [...]}`。

## 4.6 情绪看板：涨停个股（按连板分组，附题材与板块）

同样是后端接口，前端只发一个请求：

| 接口 | 作用 |
|---|---|
| `GET /api/zt-stocks` | 当天全部涨停个股，按连板数分组，每只带题材、行业板块、封单、首封时间 |

返回 `{ok, ymd, date, live, total, with_reason, groups:[{lbc, label, count, stocks:[...]}]}`，
`stocks` 里每项是 `{code, name, lbc, board, reason, fund, fbt, zbc, hs, amount, pct, days, dct}`。

**这个视图必须两个源合起来，缺一个都做不出来**（这点最容易踩）：

| 字段 | 只能从哪拿 | 说明 |
|---|---|---|
| 连板数 `lbc` / 行业板块 `hybk` / 封单 `fund` / 首封 `fbt` | 东财 `getTopicZTPool` | 同花顺这侧没有行业板块 |
| 题材 `reason_type`（`算力租赁+色纺纱`） | 同花顺 `limit_up_pool` | 东财涨停池**完全没有**题材字段 |

- ⚠️ **东财的涨停池里没有题材，别去找了**：`RPTA_WEB_ZTREASON` 之类报表名不存在
  （返回 `报表配置不存在`），东财涨停池只有 `hybk`（行业）。题材只有同花顺有。
- ⚠️ **日期必须用东财回的 `qdate` 去问同花顺，不能用「今天」**。盘前、周末、
  节假日查今天时，东财给的是上一个交易日的数据，而同花顺查那天没有涨停 →
  题材整列全空。原样对齐 `qdate` 才能保证两边是同一个交易日。
- ⚠️ **东财 `hybk` 会截断到 4 个字**：「汽车零部件」→「汽车零部」、
  「电子化学品」→「电子化学」，而同花顺题材是全称。两个都显示就像同一句话写了两遍。
  前端 `ztSplitTags()` 只在「差 1 个字」这种明显截断时合并成全称，
  **不能无脑做前缀去重** —— 那样「电池」会把「电池回收」也吞掉。
- 分组按连板数从高到低，`lbc == 1` 显示「首板」；同一梯队内按**封单金额降序**
  （封单就是资金决心，超短先看这个），封单相同再看首封时间。
- 非连续板单独标注：`zttj = {days, ct}` 里 `days != dct` 时（如「5天3板」）
  加一个灰标签，光看连板数会误判成连续 3 板。
- 缓存 25 秒（比情绪快照的 40 秒快一点，新涨停能先看到）；抓失败**退回上一次结果**，
  不把已经看到的列表清空。同花顺挂了只是题材为空，列表照常给。
- 题材缺失时显示灰标签「题材待标注」——盘中新拉的票常是这种（同花顺收盘后才补全）。
  别静默留空，那样会被当成漏渲染。
- 排查：`curl -s https://dingall-panel.onrender.com/api/zt-stocks | head -c 400`，
  正常返回 `{"ok": true, "total": 35, "with_reason": 28, "groups": [...]}`。

## 5. 解析：5 种上游格式与它们各自的陷阱

上游同一个接口有至少 5 种排版，全靠 `parse_block()` 兼容。改解析前必须知道这些：

1. **时间戳双份，且内层是 12 小时制**（最坑）
   每块有两个时间：外层块头 `YYYY-MM-DD HH:MM:SS`（24 小时制，**正确**），
   内层行 `2026-9-23 02:31:11`（同一时刻的 **12 小时制渲染**，14:30 → 02:31）。
   **一律以外层为准**，已加通用兜底：内外层偏差 > 6 小时就回退外层。
   用错内层的后果：发言在时间线里沉 12 小时，用户会报"某某没同步/有漏"。

2. **龙头舵主**：发言人固定是「老师」，正文开头的 `老师:` / `老师 ` 要剥掉。

3. **灯神（群标签格式）**：内联标签 `【计划群 · 10-21 09:58 · 灯湖】`
   含 `·` 时**只取最后一段**作为发言人。不是人名（`∴`、`10-21 09:58`）就留空，
   **绝不回退去取前面的群名**——否则「闲聊群」「系统复盘」会变成"发言人"，
   用户点它只会捞出一堆无关发言。另有 `NON_PERSON_RE` 排除"群/计划/复盘/机器人/公告/通知/助手"结尾的词。

4. **金甲（纯图片源）**：每天 09:27 发一张图，602 条几乎全是图，无正文、无发言人、无内层时间戳，
   24 小时窗口里通常只有 1~2 条。原文形如 `![]( \n\n ]( <a href="...media/xxx.png?bizType=im">详情</a>`，
   剥完会在正文残留一截 `](` → `clean_text()` 需要额外 `re.sub(r"\]\(\s*", "", s)`。

5. **金牌竞价**：块内**首行是内层时间戳**，真正的 `发言人 YYYY-MM-DD HH:MM:SS` 在**下一行**。
   `HEADER_RE` 必须能吃 4 位年份的日期，且首行是时间戳时把表头行**下移一格**再匹配。
   （2026-11-05 修过一次：修之前 602 条发言人全空，前端连名字都不渲染，用户以为"点人名没用"。）

6. **樱花哥（2026-11-19 新增）**：单人大V频道，发言账号昵称恒为「太阳的微笑」，
   消息头是 `太阳的微笑 11-19 09:53` —— **只有分钟、没有秒**。
   `HEADER_RE` 与 `parse_ts_flex` 的秒必须写成可选 `(?::\d{2})?`，否则整个源的发言人全是空。
   另外两类脏数据：
   - 纯图/网盘帖压根没有消息头（30 条左右），`链接:` 这种正文标签会被 `ROLE_RE` 误认成发言人
     → 照龙头舵主的做法**强制** `speaker = "太阳的微笑"`，图片帖才不会被"点名字只看某人"筛掉；
   - 偶发连括号一起转发（`（太阳的微笑 11-16 11:27`）→ 剥掉行首 `（`/`(`，否则多出一个假发言人。
   时间取外层（`OUTER_TIME_SOURCES` 已加入）：外层精确到秒，内层只有分钟。
   该源 602 块 = 301 条 × 2 遍，去重后约 300 条，覆盖约 6 天（日发言 20~190 条，很活跃）。

其他通用陷阱：
- 页面把内容**渲染两遍**（块数 ×2），靠 `(source, speaker, time, text)` 去重，不是 bug。
- 钉钉媒体链可能没有后缀（`static.dingtalk.com/media/...`），`IMG_RE` 要单独分支，否则裸链泄进正文。
- 第一个非空行不一定是 `lines[0]`，别硬编码 `lines[1:]`。

## 7. 部署（唯一需要注意权限的地方）

### 正常流程

```bash
git add -A && git commit -m "..." && git push
python deploy_render.py        # 或双击 deploy_render.bat
```

`deploy_render.py` 会读取 **Deploy Hook URL** 并 POST 给 Render 触发构建。

> ⚠️ **Deploy Hook URL 不在本仓库里，也不应该放进来。**
> 本仓库是**公开**的，Hook 相当于部署密码，泄露别人就能随意触发构建、刷爆免费额度。
> 原位置：用户本机 `.workbuddy/render_deploy_hook.txt`（工作区根目录下，仓库之外）。
>
> **接手时如果找不到这个文件**：去 Render Dashboard → 选服务 `dingall-panel`
> → Settings → Deploy Hook → 复制 URL，存到仓库外的一个文件里，**不要提交**。
> 或者干脆跳过脚本，在 Dashboard 点 "Manual Deploy → Deploy latest commit"。

### ⚠️ push 完 ≠ 已上线

Render 的 GitHub webhook 会**静默失败**（不报错、不通知）。实测推了 3 个 commit、40 分钟毫无动静，
而 Auto-Deploy 明明设的是 `On Commit`。所以推送后必须验证：

1. 等 2~3 分钟
2. 抓线上首页 `curl https://dingall-panel.onrender.com/ | grep <你刚加的关键字>`
3. 看 `/api/health` 的 `feed.version` 是否归零重算（说明是新进程）

对不上就手动跑一次 `python deploy_render.py`，仍不动就去 Dashboard 点 Manual Deploy。

### Auto-Deploy 三档（Dashboard → 服务 → Settings → Auto-Deploy）

- `On Commit`（推荐）：推送即构建
- `After CI Checks Pass`：**本仓库没有 CI 检查**，Render 视为 0 个检查 → **永不部署且不报错**，别选
- `Off`：只能手动或 Hook

另注：做 Rollback、或选 "Deploy a specific commit"，会**静默把 Auto-Deploy 关掉**，之后要手动重开。
`render.yaml` 里的字段已改名为 `autoDeployTrigger: commit|checksPass|off`（旧 `autoDeploy` 已废弃）。

## 8. 用户在意什么（做技术取舍时按这个来）

1. **快**。他对"比原网页慢"极度敏感，这是他推动整个重构的原因。
   任何让端到端延迟变大的改动，都要先说服他。当前上限：发帖 → 页面可见 ≤ 2 秒。
2. **不要本地服务**。以前跑过 `localhost:8899` 的本地版，2026-11-05 按他要求**全部删掉**了
   （本地服务、开机自启、桌面快捷方式）。**不要再提议"跑本地版"**，他只要线上。
3. **点人名只看这个人**。这是他最常用的功能，全靠 `speaker` 字段解析正确。
   解析出空 speaker 或把群名当人名，等于把这个功能废掉。

   筛选放在渲染层做（纯内存 filter），不要为它增加任何网络往返。
